# Corvus Durable Harness Design

Date: 2026-07-02

## Purpose

This design upgrades Corvus from a direct agent-to-tool loop into a durable local AI agent harness. The confirmed priority order is:

1. Reliable execution center
2. Strong tool system center
3. Permission and safety center

The core direction is a SQLite-backed durable harness with relation tables, append-only events, state snapshots, asynchronous tool execution, concurrency limits, recoverable runs, standardized tool manifests, approval records, and evidence storage.

## Current Project Context

The current implementation has:

- `CorvusAgent`, which directly calls the model and immediately executes tool calls.
- `ToolRegistry`, which registers tools and executes them in process.
- A simple permission policy with `allow`, `ask`, and `deny`.
- Built-in tools for file reads, file writes, directory listing, shell, web fetch, and current time.
- OpenAI Chat Completions compatible request and response handling.
- Tests for agent tool calls, tools, permissions, plugins, runtime config, commands, and TUI flow.

The current architecture works for a minimal harness but lacks durable run state, resumability, structured tool call lifecycle, approval queues, evidence storage, event audit, snapshots, output policies, and standard tool manifests.

## Confirmed Design Decisions

- Use SQLite directly as the durable local state store.
- Store the database at `.corvus/corvus.db`.
- Use a hybrid data model:
  - relation tables for current queryable state
  - append-only `events` for audit and replay
  - `state_snapshots` for fast recovery of long tasks
- Use asynchronous tool queue execution.
- Support concurrency limits.
- Support deterministic startup recovery.
- Execute first-stage tools in the current Node.js process.
- Keep shell as a subprocess behind the same tool queue lifecycle.
- Use a complete tool runtime protocol:
  - manifest
  - namespace
  - version
  - risk level
  - capability
  - resource declarations
  - JSON Schema parameter validation
  - concurrency policy
  - timeout
  - output and evidence policy
  - runtime events
- Keep first-stage permission scope at `tool:<name>` and `capability:<name>`.
- Do not implement first-stage resource-level policy or risk engine.

## SQLite Persistent Model

SQLite is the local source of truth. The database path is:

```text
.corvus/corvus.db
```

### `runs`

Represents one agent run.

Fields:

- `id`
- `status`: `created | running | waiting_for_approval | succeeded | failed | canceled | interrupted`
- `goal`
- `model`
- `endpoint`
- `created_at`
- `updated_at`
- `completed_at`

### `steps`

Represents ordered units of work within a run.

Fields:

- `id`
- `run_id`
- `index`
- `kind`: `model | tool | approval | review | system`
- `status`
- `title`
- `started_at`
- `completed_at`

### `messages`

Stores OpenAI-compatible conversation messages related to a run.

Fields:

- `id`
- `run_id`
- `role`
- `content`
- `tool_call_id`
- `created_at`

### `tool_calls`

Stores each model-requested tool call and its lifecycle.

Fields:

- `id`
- `run_id`
- `step_id`
- `tool_name`
- `capability`
- `status`: `pending | approval_required | running | succeeded | failed | denied | canceled | interrupted`
- `arguments_json`
- `result_json`
- `error`
- `timeout_ms`
- `created_at`
- `started_at`
- `completed_at`

### `approvals`

Stores tool approval decisions.

Fields:

- `id`
- `run_id`
- `tool_call_id`
- `status`: `pending | approved | denied | expired`
- `decision_scope`: `once | always | never`
- `created_at`
- `decided_at`

### `evidence`

Stores evidence generated by tools, denials, errors, setup checks, and model failures.

Fields:

- `id`
- `run_id`
- `source_type`: `tool_result | tool_error | permission_denial | model_error | system`
- `source_id`
- `title`
- `summary`
- `content`
- `created_at`

### `events`

Append-only audit log. Records every meaningful harness event.

Examples:

- `run.created`
- `run.status_changed`
- `step.created`
- `message.created`
- `tool_call.created`
- `tool_call.queued`
- `tool_call.running`
- `tool_call.succeeded`
- `tool_call.failed`
- `tool_call.denied`
- `approval.created`
- `approval.approved`
- `approval.denied`
- `evidence.created`
- `recovery.interrupted_tool_call`

### `state_snapshots`

Stores recovery snapshots for long tasks.

Fields:

- `id`
- `run_id`
- `snapshot_json`
- `created_at`

## Core Components

### `HarnessRunner`

Coordinates model calls, run lifecycle, tool call creation, queue waiting, approval pauses, evidence creation, and run completion.

Responsibilities:

- Create and resume runs.
- Persist user and assistant messages.
- Call the model.
- Convert model tool calls into durable `tool_calls`.
- Wait for tool queue completion or approval state.
- Convert tool results into OpenAI-compatible tool messages.
- Continue model loops until completion or max rounds.
- Write snapshots after major state transitions.

### `RunStore`

Owns durable run, step, and message state.

Responsibilities:

- Create runs.
- Update run status.
- Append messages.
- Create steps.
- Query resumable runs.
- Load run history.

### `ToolQueue`

Owns asynchronous tool scheduling and execution state.

Responsibilities:

- Enqueue tool calls.
- Respect per-tool, per-run, and global concurrency limits.
- Apply timeout and output limits.
- Mark pending, running, succeeded, failed, canceled, denied, and interrupted states.
- Support startup recovery.

### `ApprovalService`

Owns approval records and permission decisions that require user action.

Responsibilities:

- Create approval rows.
- Resolve approvals.
- Apply `always` and `never` decisions to permission policy.
- Return approved tool calls to the queue.
- Record approval events.

### `EvidenceStore`

Owns evidence rows and output policies.

Responsibilities:

- Create evidence from tool output.
- Create evidence from tool failures.
- Create evidence from permission denials.
- Apply truncation and evidence policy rules.
- Query evidence by id or `last`.

### `EventLog`

Appends audit events transactionally.

Responsibilities:

- Append event records.
- Preserve event order.
- Provide run event history.
- Support future replay/debugging flows.

## Runner State Machine

### `created`

- Create run.
- Store initial user message.
- Append `run.created` event.

### `running`

- Build system prompt from current config and goal.
- Call OpenAI Chat Completions compatible model.
- Store assistant message.
- If no tool calls are present, complete the run or step.

### `tool_calls_received`

- Create one `tool_calls` row per requested tool call.
- Append `tool_call.created`.
- Enqueue each tool call into `ToolQueue`.

### `waiting_for_approval`

- If any tool call requires approval, set run status to `waiting_for_approval`.
- The run remains resumable.
- The user can inspect and decide through TUI, dashboard, or commands.

### `tools_running`

- Approved or automatically allowed tool calls move to `running`.
- Tool queue executes under timeout and concurrency constraints.

### `tools_completed`

- Successful tool outputs become tool messages and evidence.
- Failed tool outputs become error tool messages and evidence.
- Denials become denial tool messages and evidence.
- Runner continues the model loop if more model work is needed.

### Terminal States

- `succeeded`
- `failed`
- `canceled`
- `interrupted`

## Recovery Behavior

At startup, Corvus scans durable state:

- `running` tool calls become `interrupted`.
- `pending` tool calls may be re-queued.
- `approval_required` tool calls remain waiting.
- `waiting_for_approval` runs remain waiting.
- `running` runs with interrupted tool calls become `interrupted`.
- `running` runs with only pending tool calls can be resumed.

`HarnessRunner.resumeRun(runId)` loads:

- Latest snapshot.
- Run messages.
- Pending tool calls.
- Approval state.
- Evidence references.

After each model call, tool completion, approval decision, denial, and terminal state change, the runner writes an event. Long-running runs also receive snapshots.

## Tool Runtime Protocol

The existing `ToolDefinition` evolves into a manifest and handler pair.

### Tool Manifest

Fields:

- `name`
- `namespace`
- `version`
- `description`
- `capability`
- `risk`: `low | medium | high`
- `parameters`
- `timeoutMs`
- `outputLimitBytes`
- `concurrency`
- `evidencePolicy`
- `resources`

`resources` are declarations for UI and future policy expansion. First-stage permission decisions do not inspect resource declarations.

### Tool Handler

The handler receives validated arguments and execution context.

The execution context includes:

- `runId`
- `toolCallId`
- `signal`
- `cwd`
- `timeoutMs`
- `outputLimitBytes`

### Tool Result

All tool results are normalized:

```ts
type ToolRunResult =
  | {
      ok: true;
      output: unknown;
      summary?: string;
      metadata?: Record<string, unknown>;
    }
  | {
      ok: false;
      error: string;
      code?: string;
      metadata?: Record<string, unknown>;
    };
```

### Validation

Before execution:

- Tool exists.
- Tool arguments match JSON Schema.
- Tool concurrency limit is available.
- Permission policy allows execution or creates approval.
- Tool call row is created.
- `tool_call.queued` event is written.

After execution:

- Result must be JSON serializable.
- Output must respect `outputLimitBytes`.
- Evidence policy is applied.
- Terminal tool state is written.
- Tool message is created for the model.
- Event log is updated.

## Tool Queue

ToolQueue is asynchronous and durable.

Statuses:

- `pending`
- `approval_required`
- `running`
- `succeeded`
- `failed`
- `denied`
- `canceled`
- `interrupted`

Concurrency policies:

- `perTool`
- `perRun`
- `global`

Timeout behavior:

- Each tool has a manifest default.
- Call-specific timeout can override within allowed limits.
- Timeout creates failed tool result and evidence.

Output behavior:

- Output is serialized.
- Output above limit is truncated.
- Truncation metadata is stored.
- Full output is only stored when policy allows.

Execution isolation:

- First-stage tools run in the current Node.js process.
- Shell commands remain subprocess calls.
- All tools are still governed by ToolQueue timeout, permission, output, and evidence policies.
- Future adapter-based sandboxing remains possible but is not a first-stage requirement.

## Permission and Approval Model

Permission scope remains:

- `tool:<name>`
- `capability:<name>`

Decision order:

1. Explicit tool rule.
2. Capability rule.
3. Default ask.

Decision outcomes:

- `allow`: queue executes the tool.
- `ask`: approval row is created; tool call becomes `approval_required`.
- `deny`: tool call becomes `denied`; denial evidence is created; denial is returned as a tool message.

Approval actions:

- Approve once.
- Deny once.
- Always allow.
- Never allow.

Permanent approval actions update current permission policy:

- `tool:<name>=allow`
- `tool:<name>=deny`

The system does not store resource-level allowlists in the first stage.

## Evidence Policy

Evidence policies:

- `none`
- `summary`
- `full`
- `full_if_error`

Rules:

- Every tool call produces at least summary evidence unless policy is `none`.
- Denials always produce evidence.
- Tool failures always produce evidence.
- Output can be truncated.
- Evidence is stored in SQLite, not config.
- API keys and configured secret values must not be stored in evidence.

Evidence can be inspected through:

- `/evidence [id|last]`
- Workbench evidence dock
- Dashboard diagnostics panel

## Commands

Future harness commands:

- `/runs`
- `/run <id>`
- `/resume <id>`
- `/cancel <id>`
- `/approvals`
- `/approve <id|all>`
- `/deny <id|all>`
- `/evidence [id|last]`

These commands should work in Line Mode and be consumable by the future Workbench and Dashboard.

## SQLite Dependency and Migrations

Recommended dependency:

- `better-sqlite3`

Reasons:

- Mature Node.js local SQLite package.
- Simple synchronous API.
- Good transaction ergonomics for CLI/TUI state transitions.
- No external SQLite server.

If native installation fails on a target machine, the implementation may use another SQLite-compatible package while preserving the same schema and store APIs.

Migration structure:

- `src/db/connection.ts`
- `src/db/migrations.ts`
- `src/db/schema.ts`

Migration table:

- `schema_migrations`

Startup behavior:

- Ensure `.corvus/` exists.
- Open `.corvus/corvus.db`.
- Apply unapplied migrations transactionally.
- Run startup recovery scan.

## Testing Strategy

### Migration Tests

- Database initializes at configured path.
- All tables exist.
- Migrations are idempotent.
- Migration rows are recorded.

### Store Tests

- Runs can be created, updated, and queried.
- Steps preserve order.
- Messages preserve role and tool call id.
- Events append in order.
- Snapshots round-trip.

### Tool Protocol Tests

- Tool manifest converts to OpenAI tool schema.
- Invalid tool arguments fail before execution.
- Tool output is normalized.
- Non-serializable outputs fail safely.
- Oversized output is truncated.

### Queue Tests

- Tool call moves pending to running to succeeded.
- Tool failure becomes failed evidence.
- Permission ask creates approval record.
- Deny creates denial evidence.
- Timeout fails a tool call.
- Concurrency limits block excess runs.

### Recovery Tests

- Running tool calls become interrupted on startup.
- Pending tool calls are re-queued.
- Approval-required tool calls remain pending approval.
- Interrupted runs are marked deterministically.

### Agent Integration Tests

- Model tool call creates durable tool call row.
- Tool result creates evidence row.
- Tool result becomes OpenAI-compatible tool message.
- Approval pauses a run.
- Approval resumes a run.
- Denial returns a structured tool message to the model.

## Acceptance Criteria

- Existing tests continue passing.
- SQLite database is created at `.corvus/corvus.db`.
- Migrations are applied once and recorded.
- A user turn creates durable run, message, step, and event records.
- A model tool call creates a durable `tool_calls` row.
- Allowed tool calls execute through ToolQueue.
- Ask permission creates an approval row and pauses the run.
- Denied tool calls create denial evidence.
- Tool outputs create evidence according to policy.
- Startup recovery handles pending, running, and approval-required tool calls deterministically.
- No API keys or secret values are written to config, SQLite, events, snapshots, or evidence.
- Current in-process tool execution remains supported.
- The design remains compatible with the approved HCI workbench spec.
